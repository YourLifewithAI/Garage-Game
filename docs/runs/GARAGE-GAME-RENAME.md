# Renaming EnFractal to the Garage Game inside the repository (planned 21 October)

**Read with** [AGENTS.md](../../AGENTS.md) and [RUN-2-STATUS.md](RUN-2-STATUS.md), "The repository split". **Status: started 21 October 2026 on the first Windows machine at the founder's word ("Can we begin the process of correcting all the names in the repo? DiamondAge isn't working on this right now, and I will update it later.").** Phases 1 to 4 are merged (phase 4 on 24 October); the founder's choices are below; phase 5 follows DiamondAge's folder rename.

The repository is `YourLifewithAI/Garage-Game` since the split, but the code still calls the game EnFractal about 3,000 times in 1,100 files. Those uses are of four kinds with very different risks, so the rename runs in phases, each tested and merged on its own. The name EnFractal now belongs to a different game (`YourLifewithAI/EnFractal`, the planetoids), so nothing here may keep it where a person or the AI reads it.

## The phases

No identifier, path, folder or data format changes.
2. **Code identifiers** (decision A; built and merged 21 October, `run2/rename-2`: the namespace `GarageGame.Native` and `GarageGame.Tests`, `GarageGame.csproj`, `.sln`, assembly and `.exe`, the package `garage_game_companion` and its commands, the agent file, the scenes' root node, every `ENFRACTAL_*` variable as `GARAGE_GAME_*` with no fallback, the `*-GarageGame*` PowerShell helpers; both runners green: release probe, companion 807 tests, NATIVE_LOOK 1562/1562). Then the founder's AI clients are registered again with `python -m <package>.profile`.
3. **The save folder** (decision B; built and merged 21 October, `run2/rename-3`: `config/name` "Garage-Game", `Saves/UserFolderMove.cs` copying the old folder's game data once on boot, verified, never overwriting, resumable, the old folder untouched, logs, caches, the companion's session and lease files left behind; the saves suite 108/108 with two mutations caught; both runners green, and the room runner's boot did a real move in its private user folder: 3 written, 416 already there, 47 kept newer). The plan was: Either keep `user://` where it is, or move it once, on the first launch of the renamed build: copy the whole folder, verify every file, leave the old one in place, and point the companion, the playtest reader, roomscan and the Linux suite at the new one in the same commit.
4. **Data-format identifiers** (decision C; built 24 October in a cloud session, `run2/rename-4`, merged on `run2/integration` with its change requests): `garage_game.<kind>` for every id. One table per language (`contracts/schema_ids.py`, `SchemaIds.cs`, `schema_ids.gd`), checked to agree, and every schema field an enum of both spellings. Writers write the new id, and readers accept both for good. The pinned files keep their bytes: the test room, the presets, rules v1 to v5, the characters, and the two pinned examples. A mutable file takes the new id at its next save, never on a read. Creation sources keep their spelling, because their hashes pin them. Both companion hosts answer `garage_game.result` to either spelling, and the link proves over the challenge's protocol. The journal is `garage-game://journal`. The canonical JSON fixture's digest `ad3d1a85…` is pinned in C#, GDScript and Python. The Linux suite is GREEN: companion 842, contracts 144, the saves suite 127/127 with a migration test. On 25 October DiamondAge ran both Windows runners (green, after a one-line test fix for Windows path separators, `94da603`) and a copy of the founder's saves: the folder move of 1,351 files, every island opened and quit cleanly, the files the game saved carry the new ids, nothing lost (RUN-2-STATUS.md, "The Windows runners on DiamondAge"). 5. **The docs' local paths,** after DiamondAge's folder is renamed to `C:\dev\Garage-Game`: AGENTS.md's worktree section, the status page's paths, the briefs. History stays as written.

- **A. The code name: `GarageGame`** (as recommended): the C# namespace, project, solution and assembly `GarageGame`, the Python package `garage_game_companion`, its commands `garage-game-companion*`. Each AI client is registered again once after phase 2.
- **B. The save folder: moved to `Garage-Game`** (the founder, 21 October: "please update everything to Garage-Game. I don't want there being any confusion in the future"). `config/name` becomes `"Garage-Game"`, so `user://` is `%APPDATA%\Godot\app_userdata\Garage-Game`; the first launch of that build copies the whole old `EnFractal` folder there, verifies every file and leaves the old folder untouched; the companion, the playtest reader, roomscan and the Linux suite look in the new folder. Phase 3.
- **C. The data-format ids: renamed with a migration** (against the recommendation to keep them). New ids `garage_game.<kind>` for all twenty kinds; readers accept both for a transition; installed rooms, saves and team files migrate; fixtures, examples and pins are regenerated; both companion hosts move in step. Phase 4, below.

## Phase 4's design (for its own session)

**What it renames.** The twenty schema ids `enfractal.<kind>` (`result`, `command`, `query`, `creation`, `room`, `island_rules`, `character`, `inventory`, `playtest_manifest`, `asset`, `team`, `glow_progress`, `player_modes`, `companion_session`, `companion_link`, `room_state`, `style`, `last_game`, `wish_adapter`, `landscape`) to `garage_game.<kind>`; the GDScript kernel's `enfractal-world-state` and `enfractal.creation-world`; the roomscan generator name `enfractal-roomscan` in manifests; the GLB extras keys `enfractal_material` and `enfractal_part` in the converter's characters; the GLB `generator` strings ("EnFractal landscape room exporter v1", the tests' "EnFractal tests"); and the name "EnFractal canonical JSON v1" with its golden fixture.

**How big (21 October, `62c57c6`).** Code that checks or writes the ids: 126 uses in 51 C# files, 141 in 44 Python files, 10 in 8 GDScript files, 36 in 10 contract schemas. Committed data that carries them: 322 files under `contracts/examples` (regenerated by `build_examples.py`), the test room (6, by its builder), the rules packs (5), the style presets (2), the characters (10 in `assets/characters`, their 10 copies in `game/characters`), the kernel and companion fixtures (9).

**The constraint.** Pinned files never change (AGENTS.md: rooms, assets and presets are hashed as bytes; a preset or rules version that is candidate, approved or pinned is never edited; saves pin them by hash). So `game/styles/storybook_painterly/v1.json`, rules packs v1 to v4, the test room and every installed room keep their old ids, and **the readers accept both ids for as long as those files exist**, not only for a transition. New versions (rules v6, preset v3, a regenerated room) are written with the new ids.

**The recommended approach.**
1. **A contract round first:** every schema's `schema` field takes either id (`enum` of the new and the old); examples and invalid examples regenerated with the new ids; one shared id table per language (C#, GDScript, Python) so a reader checks `IsSchema(value, "room")` rather than a string; the validator and both companion hosts on that table.
2. **Writers write the new id; readers accept both.** The kernel, the GDScript authority, the companion's adapter and mock, roomscan, the exporter, the playtest recorder and its reader.
3. **Mutable files migrate as they are next saved:** a team file, a vitals or Glow store, an island save read with an old id is written back with the new one the next time the game saves it, through the existing atomic writers. No pass rewrites files the player did not touch, and nothing pinned is rewritten.
4. **The companion protocol:** both hosts accept requests with either id and answer with the new one; the MCP surface's words name the new ids; the mock and the real host stay aligned (`test_kernel_alignment.py`).
5. **The canonical JSON golden fixture** is regenerated under its new name, its SHA-256 updated in the C#, GDScript and Python checks together.
6. **The characters' GLB keys:** the readers accept `garage_game_part` and `garage_game_material` beside the old keys; the converter writes the new ones; the committed GLBs keep theirs until the next conversion.

**Acceptance:** the contract tests and every alignment test green; both Windows runners and the Linux suite; a migration test on a copy of the founder's real saves (DiamondAge) showing every island, team and installed room loads before and after, and the files the game saves carry the new ids; pinned files byte-identical.

**Routing:** Opus, a fresh session (a contract round touching the kernel, persistence and the companion boundary), on DiamondAge or here; one fresh Opus reviewer after.
